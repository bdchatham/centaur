- (capability) CAP-2: each failed attempt's entry carries error = the attempt's failure message; non-failed entries have error null, so the same error across retries is readable by comparing entries.
- (capability) CAP-3: unknown run -> 404, ok false, same error body as the full run endpoint.
- (capability) CAP-4: no input/result/failure payload or run/task ids beyond the entry's own fields appear in the body.
- (constraint) Entries are reused unchanged from spec-run-attempts: this brief defines no entry field and adds none to the attempt history. The attempts spec currently fixes entries at exactly attempt, started_at, ended_at, outcome (CAP-1, CAP-4, story 1) so it must itself carry error; raised as a challenge on that spec and its story 1.
- (constraint) Report and /attempts share one attempt-entry reader so they cannot drift; no second query path.
- (constraint) route_access needs a GET entry mapped to WorkflowsRead.
- (constraint) Proof by new Rust test files under services/api-rs/crates/centaur-api-server/tests/, HTTP only, DB-backed tests skip without a database URL, seeding absurd t_/r_ tables as run_timestamps.rs does; red before the change because the route is missing.
- (decision) One story: the route, shared entries and 404 are one reviewable slice; error is the attempts brief's field, so a separate story over it would not be red-then-green here.
- (assumption) Body envelope {ok: true, attempts: [...]} as sibling routes; no report-level summary fields.
- (assumption) error is the string 'message' member of the attempt's failure_reason; null if the attempt did not fail or its failure has no string message.
- (assumption) A run that was never retried still returns 200 with its single entry; only an unknown run is 404.
- (question) Should the report add a summary (e.g. same_error boolean or distinct error list) or is comparing entries enough?
- (question) Should the report list only failed attempts, or all attempts as specified?

- (question) Does a very long failure message need truncation?
