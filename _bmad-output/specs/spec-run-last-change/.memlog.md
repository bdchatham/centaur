- (direction) Brief (human/engineer, mark bafyreidkoi432...): updated_at on GET /api/workflows/runs and /{run_id} must be the time of the last real change in every state; finished runs report finish time; no run reports a future time. Input run mode: headless, express.
- (note) Code: centaur-workflows/src/lib.rs list_runs_for_queue (~L960) and get_run_for_queue (~L1030) duplicate SQL computing updated_at = greatest(enqueue_at, case when sleeping or infinite available_at then coalesce(started_at, created_at) else coalesce(available_at, enqueue_at) end).
- (note) Absurd (migration 0007): claim sets run started_at = available_at = claim time; complete/fail set only completed_at/failed_at and leave available_at; cancel_task sets only task cancelled_at, leaving run available_at (future wake for a sleeping run); sleep sets available_at to wake time.
- (note) Prior stories already fixed sleeping runs (greatest(enqueue_at, coalesce(started_at, created_at))) and infinite-wait runs; terminal and pending states untouched.
- (note) Existing tests sleeping_updated_at.rs and wait_updated_at.rs pin completed_run updated_at = ENQUEUED (enqueue_at) and pending_run updated_at = FAR_FUTURE; both pin the behavior the brief calls wrong, so they must change; the delivery PR flags such edits.
- (capability) CAP-1: completed and failed runs report their finish time (completed_at / failed_at of the last attempt) as updated_at.
- (capability) CAP-2: cancelled runs report the cancellation time (task cancelled_at) as updated_at, including runs cancelled while sleeping, which today show their future wake time.
- (capability) CAP-3: no run reports a future updated_at in any state; pending runs whose available_at is in the future report their last real change instead.
- (capability) CAP-4: list_runs, get_run, and both HTTP routes agree on updated_at, for all four workflow queues.
- (decision) Terminal-state rule: completed -> run completed_at, failed -> run failed_at, cancelled -> task cancelled_at, each floored at enqueue_at; same expressions as the existing completed_at output column, so updated_at equals completed_at for finished runs.
- (decision) Running runs keep claim time (available_at = started_at at claim); no change needed.
- (decision) Pending: available_at when it is not in the future (a woken run's wake time, or enqueue time); otherwise the later of enqueue_at and the attempt row's created_at (when the attempt was scheduled). Never now()-clamping, which would make updated_at drift between reads.
- (decision) Constraint: no migration, no change to field names/types, no change to list ordering (still created_at desc), no change to started_at/completed_at/created_at.
- (decision) Stories: 1 finished completed/failed; 2 cancelled incl. sleeping; 3 pending not future. Existing-test edits: completed_run expectation (stories 1) and pending_run expectation (story 3) in sleeping_updated_at.rs and wait_updated_at.rs.
- (assumption) A cancelled run's last real change is the cancellation request time (cancelled_at), even if the attempt was still winding down.
- (question) Pending runs with a future available_at (scheduled start or retry delay): is the later of enqueue_at and the attempt row creation the right last real change, or should a retry-pending run report the previous attempt's failure time? Both are past times; chosen: attempt row created_at, which Absurd sets when the retry is scheduled.
- (question) Should packages/api-client types or the console UI doc comments describing updated_at be updated? Not found referencing updated_at for workflow runs in this repo; assumed out of scope.
- (question) Ordering of list_runs is by created_at, not updated_at; should it change? Brief does not ask; left as is.
