- (direction) Input brief (mark bafyreicwhes...jve, goal run-steps): add GET /api/workflows/runs/{run_id}/steps to the api-rs workflow-runs API: the run's step history as a list of entries (step name, state, started_at, completed_at), oldest first, for clients debugging a run without fetching its inputs and outputs; unknown run is 404; every story in stories.yaml sets spec_checkpoint: true (human reviews each story before work starts).
- (event) Mode: headless, express. Slug: run-steps.
- (note) Code ground: routes in services/api-rs/crates/centaur-api-server/src/routes.rs (/api/workflows/runs/{run_id} -> get_workflow_run -> WorkflowRuntime::get_run, returns {ok:true, run}); route_access() maps each (method, route) to a capability and unmapped routes are denied, so the new route needs a WorkflowsRead entry like the sibling GETs. WorkflowRuntimeError::NotFound maps to 404 {ok:false, error:'workflow run not found: <id>'}. get_run searches four queues (workflow, slack-live, etl, etl-backfill) over absurd.t_<queue>/r_<queue>; get_run_for_queue is private and returns the full WorkflowRun.
- (note) Step data ground: the only durable per-step record is the Absurd checkpoint table absurd.c_<queue> (task_id, checkpoint_name, state jsonb, status default 'committed', owner_run_id, updated_at; pk task_id+checkpoint_name; created by migration 0007). The SDK writes a row when a step completes (begin_step/complete_step, sleep_for, await_event); checkpoint_name is the step name, with suffix #N for the Nth use of the same name in one attempt. state jsonb is the step's output payload; there is no start-time column and no in-progress row. absurd.get_task_checkpoint_states already defines a run's visible checkpoints: committed, owner run attempt <= the run's attempt, ordered by updated_at asc. Runs are per-attempt rows (r_<queue>.run_id); checkpoints hang off task_id and are shared across attempts.
- (note) Existing tests seed absurd.t_<queue>/r_<queue> rows directly and read via the router (centaur-api-server/tests/run_timestamps.rs, runs_by_state_http.rs); database-backed tests skip without a database URL. No test seeds c_<queue> yet; no checkpoint read exists in centaur-workflows.
- (capability) CAP-1: a client can fetch GET /api/workflows/runs/{run_id}/steps and receive the run's steps, each with exactly name, state, started_at, completed_at.
- (capability) CAP-2: steps are ordered oldest first by completion time, the order the run executed them.
- (capability) CAP-3: the step list carries no step input or output: the checkpoint state payload is never returned.
- (capability) CAP-4: an unknown run id returns 404 with the same error body as the full run endpoint; a run that exists but has no steps returns 200 with an empty list.
- (decision) step name is the checkpoint_name as stored, including the #N suffix for repeated steps, so every entry is distinct and can be matched to the checkpoint table.
- (decision) state is the checkpoint row's status string (today always 'committed'), not the checkpoint state payload: the brief says clients should not fetch inputs and outputs, and the payload is the step's output. Only completed steps have rows, so every listed step is committed.
- (decision) completed_at is the checkpoint row's updated_at as RFC 3339 (the time the step's result was committed). started_at is a required key whose value is null for every step, because no start time is stored for a step; recording one needs a migration and SDK change the brief does not ask for.
- (decision) Visibility and order follow absurd.get_task_checkpoint_states: only committed checkpoints of the run's task whose owner attempt is <= the requested run's attempt; ordered by completed_at ascending with checkpoint name as tie-break. Reading from the same table the SDK reads keeps history and resume agreeing.
- (decision) Body shape follows sibling routes: {"ok": true, "steps": [ ... ]}.
- (decision) Single story: the route, its route_access entry and the checkpoint read are one slice; an unknown-run 404 slice would not be red-then-green because the 404 falls out of the same run lookup, and the proof is HTTP-only so new tests compile before the change and fail because the route is missing.
- (constraint) Additive only: existing routes, WorkflowRun, and get/list responses keep their shape; no migration (c_<queue> exists); durable Postgres state only, no process-local source.
- (constraint) Entry keys are exactly name, state, started_at, completed_at; no state payload, input, result, failure, task or run ids.
- (constraint) The new route needs a route_access entry mapped to Capability::WorkflowsRead, like sibling GET run routes.
- (constraint) Proof is new Rust test files under services/api-rs/crates/centaur-api-server/tests/; each test compiles before the change and fails because the route is missing, so tests use only existing items (build_router_with_session_and_workflow_runtime, console token, direct seeding of absurd tables incl. c_<queue>) and assert on HTTP status and JSON. Existing tests may be edited where the design needs; the CI oracle flags such edits.
- (decision) Non-goals: step payloads/input/output, started_at values, in-progress or pending steps, sleep/await-event wait rows (absurd.w_<queue>), pagination or filters, steps on the full run or list routes, packages/api-client or UI, caching, special handling of non-UUID run ids.
- (assumption) Run id means a run row id as on the full endpoint; steps are those of the run's task visible to that run (attempt rule above), so a retried task's earlier attempt run sees fewer steps than its latest run.
- (assumption) A step that appears in the history is complete; no running-step entry exists because the SDK writes a checkpoint only on completion.
- (assumption) completed_at ties are broken by name ascending; the SDK writes one checkpoint per step so ties arise only from identical commit instants.
- (question) started_at: no step start time is stored, so the spec returns null for every step. Should started_at be dropped, derived (e.g. previous step's completed_at, or the attempt's started_at for the first step), or backed by a new column recorded when a step begins (migration + absurd-sdk change)?
- (question) state: is the checkpoint status string ('committed') what 'state' means, or should it be a richer state (e.g. pending/running/completed) including steps not yet finished?
- (question) Envelope: {"ok": true, "steps": [...]} (assumed, matches sibling routes) or a bare list?
- (question) Should sleep and await-event steps (which persist checkpoints under names like the step name or $awaitEvent:<event>) be listed as ordinary steps (specified) or distinguished?
- (question) Non-UUID run_id: get_run casts to uuid, so a malformed id may yield 500 rather than 404 today; should /steps answer 404 or 400?
- (question) Should a retried run's history include checkpoints from earlier attempts (specified, matching the SDK's visibility rule) or only those owned by the requested run?
- (event) Self-validate pass 1 (coherence) and pass 2 (preservation): every brief claim landed (route, four fields, oldest first, no payloads, 404, per-story spec_checkpoint); CAPs have intent+success; gaps (started_at, state meaning, envelope, wait steps, attempt visibility, malformed id) recorded as questions, none invented.
- (event) stories.yaml written (1 story); schema check ok: id quoted, unique, prefix-free, no status, two-sentence description, spec_checkpoint true as the brief requires.
