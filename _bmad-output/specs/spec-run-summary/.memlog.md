- (direction) Input brief (mark bafyreih3phj...apuni, goal run-summary): add GET /api/workflows/runs/{run_id}/summary returning one small JSON object per run: run_id, workflow_name, status, attempt count, created_at, updated_at, for clients wanting a run's headline without steps/results; unknown run is 404; every story in stories.yaml sets spec_checkpoint: true (human reviews each story before work starts).
- (event) Mode: headless, express. Slug: run-summary.
- (note) Code ground: routes in services/api-rs/crates/centaur-api-server/src/routes.rs (/api/workflows/runs/{run_id} -> get_workflow_run -> WorkflowRuntime::get_run; returns {ok:true, run}). route_access() maps each (method, route) to a capability; unmapped routes get 403, so the new route needs a WorkflowsRead entry like the sibling GETs. WorkflowRuntimeError::NotFound maps to 404 with body {ok:false, error:'workflow run not found: <id>'} in error.rs.
- (note) WorkflowRun (centaur-workflows/src/lib.rs) already has run_id, workflow_name, status (Absurd task state), attempts (i32, task attempts), created_at (=enqueue_at), updated_at, plus input/result/failure/started_at/completed_at. get_run searches the four queues (workflow, slack-live, etl, etl-backfill) via get_run_for_queue, which also decodes params and completed_payload.
- (note) Existing tests seed absurd.t_<queue>/r_<queue> rows directly and read via the router (centaur-api-server/tests/run_timestamps.rs, runs_by_state_http.rs); database-backed tests skip without a database URL.
- (capability) CAP-1: a client can fetch GET /api/workflows/runs/{run_id}/summary and receive one small object with exactly run_id, workflow_name, status, attempts, created_at, updated_at.
- (capability) CAP-2: the summary agrees with the full run: for the same run, each summary field equals the same field of GET /api/workflows/runs/{run_id}, for runs from all four queues and every run state.
- (capability) CAP-3: an unknown run_id yields 404 with the standard error body, same as the full run endpoint.
- (constraint) Additive only: existing routes, WorkflowRun, and list/get responses unchanged.
- (constraint) Summary field values are identical to the full run's (status string, updated_at semantics, RFC 3339 timestamps like created_at); no re-derivation that could diverge. The summary omits input, result, failure, task ids, started_at, completed_at (headline only).
- (constraint) Route needs a route_access entry mapped to Capability::WorkflowsRead, same as the sibling GET run routes; absent it every caller gets 403.
- (constraint) Values come from durable Absurd state in Postgres; no process-local state, no migration (api-rs AGENTS.md).
- (decision) Response envelope follows the sibling routes: {ok:true, summary:{...}}, not a bare object, so clients handle ok/error uniformly. Raised as an open question since the brief says 'one small JSON object'.
- (decision) Attempt count is exposed as key attempts (same name and value as WorkflowRun.attempts); the brief says 'attempt count' without a key name.
- (decision) Single story: the route cannot be split into a red-then-green 404 slice because an absent route already returns an error and the 404 for an unknown run falls out of the same lookup; proof is HTTP-only so tests compile before the change.
- (constraint) Proof is new Rust test files under crates/centaur-api-server/tests/; each test compiles before the change and fails because the route is missing, so tests only use existing items (build_router_with_session_and_workflow_runtime, console token) and assert on HTTP status and JSON. Existing tests may be edited where the design needs; the CI oracle flags such edits.
- (decision) Non-goals: steps, input, result, failure, started_at/completed_at in the summary; a list-summaries endpoint; changing updated_at or status semantics; packages/api-client or UI changes; caching.
- (assumption) Run ids with a non-UUID form behave as on the full endpoint (get_run binds run_id as uuid), i.e. not specially handled by this work.
- (question) Envelope: should the body be {ok:true, summary:{...}} (assumed, matches sibling routes) or the bare object?
- (question) Is 'attempt count' the task-level attempts value the full run reports (assumed), and should the key be named attempts?
- (question) Non-UUID run_id: get_run casts to uuid, so a malformed id may yield 500 rather than 404 on the full endpoint; should the summary return 404 (or 400) for it?
- (question) Should status be the raw Absurd state string (pending, running, sleeping, completed, failed, cancelled) as in the full run (assumed)?
