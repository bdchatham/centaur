- (direction) Input brief (mark bafyreic63...ol24xu, goal workflow-run-timestamps): expose started_at and completed_at on every workflow run the API returns; null until set; so clients show durations without inferring from updated_at.
- (event) Mode: headless, express. Slug: run-timestamps.
- (note) Code ground: WorkflowRun in services/api-rs/crates/centaur-workflows/src/lib.rs (fields run_id..attempts, created_at, updated_at; rfc3339 serde). Built by workflow_run_from_row from list_runs_for_queue/get_run_for_queue SQL over absurd t_/r_ tables; list_runs merges 4 queues (workflow, slack-live, etl, etl-backfill). Routes GET /api/workflows/runs and /{run_id} in centaur-api-server/src/routes.rs return the struct as JSON.
- (note) Absurd schema (migration 0007) already has r.started_at, r.completed_at, r.failed_at per run attempt, t.first_started_at, t.cancelled_at on task. No new migration appears needed; updated_at today is greatest(enqueue_at, available_at), not a real timestamp of activity.
- (capability) CAP-1: every workflow run returned by the API carries started_at: when execution began, null until then.
- (capability) CAP-2: every workflow run returned by the API carries completed_at: when execution finished, null until then.
- (capability) CAP-3: both fields are present and consistent on list and get endpoints, for runs from all four workflow queues.
- (constraint) Additive only: existing fields (incl. updated_at) keep name, type, and semantics; new fields always serialized (null, never omitted) as RFC 3339 like created_at.
- (constraint) Values come from durable Absurd state in Postgres, not process-local state; no new migration unless the existing columns prove insufficient (api-rs AGENTS.md: Postgres is the source of truth).
- (constraint) Tests are Rust tests in services/api-rs; DB-backed tests skip without a database URL per AGENTS.md.
- (decision) started_at = first time any attempt began executing (task first_started_at), so a retried run keeps its original start; it stays null while the run is pending and never claimed.
- (assumption) completed_at is set when the run reaches a terminal state (completed, failed, cancelled) and null otherwise, including while a failed attempt awaits retry.
- (question) Retries: should started_at be the first attempt's start (assumed) or the latest attempt's? And should completed_at/duration for a retried run cover the whole task or only the last attempt?
- (question) Cancelled runs: Absurd records task.cancelled_at; should completed_at equal cancellation time, or stay null because the run did not finish?
- (question) Cancelled-before-start runs: started_at stays null but completed_at is set (assumed)? Confirm clients tolerate completed_at without started_at.
- (question) Should packages/api-client (TypeScript types) and other consumers be updated in this work? Assumed out of scope.
- (decision) Non-goals: changing updated_at semantics; adding duration fields; schema migration/backfill; client/UI changes; per-attempt history.
- (decision) Success signal: Rust tests show pending run -> both null, running -> started_at set/completed_at null, completed/failed/cancelled -> completed_at set, on list and get, serialized as RFC 3339 or null.
- (decision) Story slicing: 1 type+serialization, 2 query mapping across queues, 3 HTTP list/get end-to-end.
