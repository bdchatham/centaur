- (direction) Input brief (mark bafyreib5e3gz..., goal workflow-runs-by-state): GET /api/workflows/runs?state=<state> returns only runs in that state (pending, running, sleeping, completed, failed, cancelled), combined with existing limit and workflow_name filters; unknown state is 400 naming the valid ones; goal is telling whether any run is live without paging.
- (event) Mode: headless, express. Slug: runs-by-state.
- (note) Code ground: ListWorkflowRunsQuery{limit,workflow_name} in centaur-api-server/src/types.rs; list_workflow_runs in routes.rs calls WorkflowRuntime::list_runs(limit, workflow_name). list_runs (centaur-workflows/src/lib.rs) queries four queues (workflow, slack-live, etl, etl-backfill) via list_runs_for_queue, each with SQL 'limit $1' and workflow_name predicate, then merges, sorts by created_at desc and truncates. Run status = Absurd t.state, already exactly pending|running|sleeping|completed|failed|cancelled. 8 existing tests under centaur-api-server/tests call list_runs(100, Some(name)).
- (note) ApiError maps WorkflowRuntimeError::BadRequest to HTTP 400. Router with no workflow runtime also answers 400 ('workflow runtime is not enabled'), so state validation must precede runtime lookup for a DB-free test of the unknown-state 400.
- (capability) CAP-1: GET /api/workflows/runs?state=<state> returns only runs whose status equals state, for each of the six states.
- (capability) CAP-2: state combines with limit and workflow_name; the state filter applies before limit so limit counts matching runs only.
- (capability) CAP-3: an unknown state is a 400 whose message names all six valid states; without state behaviour is unchanged.
- (decision) Filter in SQL per queue (before 'limit'), not post-filter in Rust: post-filtering a limited page would drop live runs behind newer terminal ones, defeating the goal.
- (decision) State is a typed WorkflowRunState enum in centaur-workflows with FromStr/as_str and an ALL list; list_runs gains a state: Option<WorkflowRunState> parameter (existing 8 test call sites pass None; oracle flags the edits). Route parses state before looking up the runtime.
- (constraint) Additive: no state = identical results; response shape unchanged; state values match WorkflowRun.status strings exactly and are lowercase and case-sensitive.
- (constraint) Proof is by new Rust tests in new files under tests/ of touched crates; DB-backed tests skip without a database URL; unknown-state 400 test must run without a database.
- (decision) Non-goals: multiple states per request, state in other list routes, cursor pagination, new indexes/migration, api-client or UI changes, changing how status is derived.
- (decision) Success signal: with runs seeded in all six states, ?state=X returns exactly the matching runs (combined with limit/workflow_name), unknown state is 400 naming valid states, no-state output unchanged.
- (question) Is state matching case-sensitive (assumed) or should 'Running' be accepted?
- (question) Should an empty ?state= be treated as absent or as an unknown state (assumed: unknown, 400)?
- (question) Should packages/api-client (listWorkflowRuns types) and docs/pages/extend/workflows*.mdx gain the new parameter? Assumed out of scope.
- (question) Does a task with state running whose lease expired still count as running? Assumed yes: state is Absurd t.state as reported today.
- (decision) Story slicing: 1 WorkflowRunState type, 2 runtime list_runs state filter across queues, 3 HTTP query param with 400.
