- (direction) Input brief (mark bafyreiffoxbhg..., goal runs-created-after, human/alice): GET /api/workflows/runs?created_after=<RFC 3339> returns only runs created strictly after that time, newest first as today, combined with limit, workflow_name, state; invalid timestamp is 400; every story sets spec_checkpoint: true.
- (event) Mode: headless, express; slug runs-created-after.
- (note) Code read: routes.rs list_workflow_runs parses ?state before workflow_runtime(&state); ListWorkflowRunsQuery in types.rs; WorkflowRuntime::list_runs_by_state fans out over 4 queues with per-queue SQL (order by t.enqueue_at desc, limit) then merges and truncates; created_at = t.enqueue_at; routes.rs parse_rfc3339_option exists but treats empty as absent.
- (capability) CAP-1: client lists only runs whose created_at is strictly after ?created_after (RFC 3339), newest first.
- (capability) CAP-2: created_after composes with limit, workflow_name and state; limit counts matching runs.
- (capability) CAP-3: a created_after value that is not valid RFC 3339 is HTTP 400 naming the parameter; absent param behaves as today.
- (constraint) Filter runs in SQL per queue before limit (t.enqueue_at > bound), as state does; filtering a fetched page in Rust would hide matching runs behind newer non-matching ones... actually would drop nothing newer but wastes limit; keep in SQL for consistency with state and correct limit semantics.
- (constraint) Strictly after: a run created exactly at the bound is excluded; offsets are normalised to an instant, so 10:00:00+02:00 equals 08:00:00Z.
- (constraint) Parse created_after before the workflow runtime lookup so an invalid value is a 400 whatever runtime availability; this gives DB-free red tests.
- (constraint) Additive only: response shape, ordering, default limit unchanged; no migration; no new index.
- (constraint) Proof via HTTP route only, new test file under centaur-api-server/tests using no symbol this work adds; DB-backed tests skip without SESSION_SQLX_TEST_DATABASE_URL; invalid-value 400 tests need no DB and carry red-then-green there. Helper types and list_runs shape are dev's choice; existing tests edited only if design requires.
- (decision) One story covers CAP-1..3: parsing, SQL filter and composition are not separately useful (a param accepted but ignored for valid values would be a regression in honesty), and the 400 tests are the DB-free red. spec_checkpoint: true per brief.
- (assumption) Valid means accepted by time's Rfc3339 parser (full date-time with offset or Z); date-only and offset-less values are 400. A literal + in an offset must be percent-encoded in the URL as with any query string.
- (assumption) Empty ?created_after= is invalid (400), consistent with the state filter, not absent.
- (assumption) A bound in the future returns an empty runs list with HTTP 200.
- (question) Should sub-microsecond precision in created_after matter? Postgres timestamptz holds microseconds; bound is passed through as given (assumed: no special handling).
- (question) Should packages/api-client types and docs/pages/extend/workflows*.mdx document the parameter in this work (assumed: no)?
- (decision) Non-goals: created_before / ranges, filters on updated_at/started_at/completed_at, cursor pagination, ordering change, new indexes, api-client or docs updates.
- (decision) Clarifies the SQL-filter constraint: the bound is applied in each queue's SQL before limit so limit counts matching runs; a per-queue page cut by limit then filtered in Rust could return fewer than limit matches even when more exist.
