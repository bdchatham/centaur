---
topic: Workflow run updated_at must never be a future time for sleeping, timed-wait, and backoff runs
updated: 2026-10-14T22:33
---

- (direction) Brief (express, headless): updated_at on GET /api/workflows/runs and /{run_id} must say when the run last changed, never a future time; runs that sleep, wait on an event with timeout, or back off before a retry report their wake/retry time today and must report their last real change instead.
- (note) Code: centaur-workflows/src/lib.rs list_runs_for_queue and get_run_for_queue compute updated_at = greatest(t.enqueue_at, case when available_at is non-finite then coalesce(r.started_at, r.created_at) else coalesce(r.available_at, t.enqueue_at) end). Prior story (spec-wait-updated-at) fixed only the 'infinity' no-timeout case.
- (note) Absurd (migration 0007): claim sets run.started_at = available_at = claim time; schedule_run (sleep) and await_event with timeout set state='sleeping', available_at = wake/timeout time; fail_run with backoff inserts a new run, state='sleeping' when next available is in the future, created_at = failure time, available_at = now+backoff; emit_event sets state='pending', available_at = emit time.
- (note) Tests today: wait_updated_at.rs seeds a pending run with available_at=2099 expecting updated_at 2099 (synthetic; real Absurd never makes a pending run with future available_at); run_timestamps.rs seeds FAR_FUTURE available_at on pending/cancelled runs but only asserts updated_at is a string.
- (capability) CAP-1: a sleeping run (sleep, timed event wait, retry backoff) with a finite future available_at is returned by get_run and GET /{run_id} with updated_at equal to its last real change, not available_at.
- (capability) CAP-2: such runs list through list_runs and GET /api/workflows/runs with the same updated_at as get, on all four queues (workflow, slack-live, etl, etl-backfill).
- (capability) CAP-3: no run in the sleeping state reports an updated_at later than it could have been written; updated_at never precedes enqueue_at, so list ordering by updated_at is not distorted by wake times.
- (decision) Last real change for a sleeping run = greatest(enqueue_at, coalesce(run.started_at, run.created_at)): the attempt's claim time for sleep/timed-wait, the failure time (new run created_at) for backoff. Same expression the no-timeout case already uses, so the non-finite branch generalises to state='sleeping'.
- (constraint) Runs not in the sleeping state keep today's updated_at value exactly (pending, running, completed, failed, cancelled).
- (constraint) Read-side fix in the list and get queries in centaur-workflows for all four queues; Absurd's stored available_at and its migrations stay as they are.
- (constraint) WorkflowRun field names, types, and non-null RFC 3339 updated_at unchanged; no new fields; non-finite available_at stays handled.
- (constraint) Proof is by new Rust tests in a new file under services/api-rs/crates/centaur-api-server/tests/, seeding Absurd rows directly as wait_updated_at.rs does; db tests skip without a database URL; tests call only existing items (list_runs/get_run, routes) so they compile pre-change and fail on the wrong updated_at. Existing tests may be edited where the design needs it; the oracle flags such edits.
- (assumption) Absurd never produces a pending run with a future available_at (a retry due in the future is state 'sleeping'), so the 2099 pending seed in wait_updated_at.rs is synthetic and out of scope.
- (assumption) The attempt's started_at is an acceptable proxy for the moment a sleep or timed wait began; Absurd does not record that moment on the run row.
- (question) Cancelled while sleeping: Absurd cancels the run without touching available_at, so a cancelled run can still report the wake time as updated_at (future). Should cancelled runs report cancelled_at instead?
- (question) Should a sleeping run's updated_at be the moment the wait began (absurd waits table created_at, event waits only) rather than the attempt's start?
- (question) Should updated_at for completed/failed runs reflect completion time rather than claim time (available_at)? Out of scope here; today's value is kept.
- (question) Do packages/api-client or the UI sort or display updated_at in a way that needs a change?
- (decision) Single story: one SQL change in both queries; splitting by sleep kind or list vs get would yield tests that already pass (no red-then-green).
