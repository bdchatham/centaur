topic: Workflow runs waiting on an event with no timeout must list with a finite updated_at
updated: 2026-10-14T20:36
---

- (direction) Brief (express, headless): GET /api/workflows/runs and /{run_id} must keep working while a run waits on an event with no timeout; waiting run lists normally with updated_at reflecting its last real change.
- (note) Code: centaur-workflows/src/lib.rs list_runs_for_queue and get_run_for_queue compute updated_at = greatest(t.enqueue_at, coalesce(r.available_at, t.enqueue_at)); workflow_run_from_row decodes it into OffsetDateTime.
- (note) Cause: absurd await_event (migrations 0007, 0009) sets run.available_at = coalesce(timeout_at, 'infinity') for a no-timeout wait; greatest() returns infinity, row decode fails, list 500s.
- (capability) CAP-1: a run waiting on an event with no timeout is returned by get_run/GET /{run_id} with a finite RFC 3339 updated_at.
- (capability) CAP-2: one such waiting run does not break GET /api/workflows/runs; other runs in the list still return.
- (capability) CAP-3: updated_at for a waiting run reflects its last real change, never infinity or a far-future sentinel.
- (constraint) Runs whose available_at is finite keep today's updated_at value exactly; only the non-finite case changes.
- (constraint) Fix is read-side in the api-rs workflow-runs queries (list and get, all four queues); Absurd's stored available_at = infinity is the scheduler's contract and stays.
- (constraint) WorkflowRun field names/types unchanged; updated_at stays non-null RFC 3339.
- (constraint) Proof is by new Rust tests under centaur-api-server/tests seeding Absurd rows directly (pattern of run_timestamps.rs); db tests skip without a database URL; tests call only existing items (list_runs/get_run, the routes) so they compile pre-change and fail on the 500/decode error.
- (decision) Waiting run's updated_at = greatest(enqueue_at, coalesce(run.started_at, run.created_at)): latest durable timestamp of the attempt that went to sleep. Chosen over joining the waits table to avoid extra join; see open question.
- (assumption) Postgres infinity (and -infinity) are the only non-finite values; a finite future available_at (timed wait, retry backoff) is out of scope and unchanged.
- (question) Should updated_at for a waiting run be the moment the wait began (absurd waits table created_at) rather than the attempt's start/creation? Spec assumes attempt timestamps.
- (question) Should a finite future available_at (timed wait/backoff) also stop being reported as updated_at (it is a future time)? Out of scope here.
- (question) Should packages/api-client or UI be checked for handling of waiting runs? Out of scope here.
- (decision) Single story: the runtime SQL change in both queries is one slice, and splitting list from get/route would yield tests that already pass (no red-then-green).
