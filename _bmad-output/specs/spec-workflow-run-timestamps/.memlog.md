topic: Expose started_at and completed_at on api-rs workflow runs
updated: 2026-10-13T21:48
---

- (direction) Express headless mode; brief: expose started_at and completed_at on every WorkflowRun the api-rs workflow-runs API returns; null until then; so clients show durations without inferring from updated_at
- (note) Grounding: WorkflowRun struct in services/api-rs/crates/centaur-workflows/src/lib.rs (~l.377) has created_at/updated_at only; built by workflow_run_from_row from list_runs_for_queue/get_run_for_queue SQL over absurd t_/r_ queue tables; served by routes list_workflow_runs/get_workflow_run in centaur-api-server/src/routes.rs; absurd schema already has t.first_started_at, r.started_at, r.completed_at, r.failed_at, t.cancelled_at
- (note) updated_at today is greatest(t.enqueue_at, coalesce(r.available_at, t.enqueue_at)), an approximation, not completion time
- (capability) CAP-1 WorkflowRun JSON carries started_at and completed_at as RFC3339 strings or null, serialized like created_at/updated_at; always present as keys
- (capability) CAP-2 started_at is null while run is queued and set once execution began; completed_at is null until the run reaches a terminal state, then set
- (capability) CAP-3 Both fields appear on every endpoint returning a WorkflowRun: GET /api/workflows/runs list and GET /api/workflows/runs/{run_id}, across all four workflow queues
- (constraint) Additive only: existing WorkflowRun fields and their semantics (including updated_at) unchanged; existing clients keep working
- (constraint) Values come from the stored Absurd run/task timestamps, not computed from updated_at or wall clock at read time, so repeated reads are stable
- (constraint) Every story must be provable by Rust tests in services/api-rs; DB-backed tests in this repo skip unless a test DATABASE_URL env var is set, so SQL-to-struct logic should be unit-testable without a database
- (decision) Non-goals: no duration field, no change to updated_at, no new filters/sorting by these fields, no change to CreateWorkflowRunResponse, no TS api-client or UI changes, no schema migration unless Absurd columns prove insufficient
- (question) Which timestamp is started_at on a retried run: task t.first_started_at (first attempt began) or r.started_at of the latest attempt (the run row returned)? Brief says 'when it started executing'; undecided
- (question) For failed and cancelled runs, is completed_at set (to r.failed_at / t.cancelled_at) or does it mean successful completion only? Brief says 'when it finished'; undecided
- (question) While a run is sleeping/awaiting an event or being retried after failure (non-terminal), should completed_at stay null? Assumed yes
- (question) Does the TS api-client (packages/api-client) type for runs need the new fields? Its shape (items/WorkflowRunAccepted) differs from the Rust response (runs); out of scope pending confirmation
- (assumption) Assumed the observed API is the Rust WorkflowRun JSON (ok/runs, ok/run); timestamps nullable RFC3339 via time::serde::rfc3339::option
- (decision) Stories: 1 model+serialization, 2 SQL queries and row mapping populate fields, 3 route-level JSON exposure for list and get
- (event) Self-validate pass 1 (coherence): rules 1-6,8 satisfied; 4 open questions/assumptions recorded not invented
- (event) Self-validate pass 2 (preservation): brief claims all landed in kernel; no wrapper-only drops
- (event) stories.yaml written by pm outside Story Breakdown; checked against schema: quoted unique prefix-free ids, no status, no checkpoints
